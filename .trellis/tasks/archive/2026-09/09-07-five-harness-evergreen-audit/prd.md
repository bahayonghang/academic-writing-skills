# 五套 Harness 能力边界与常青维护审查

## Goal

基于当前仓库、现有测试及一手 harness 文档，形成可批准、可逐项验收的常青维护改造计划，覆盖 Claude Code、Codex、Grok Build、Kimi Code、Oh My Pi（OMP）。

## Requirements

- R1：说明项目结构、关键入口、规则所有权和发布链路。
- R2：运行现有质量门禁，保存命令、退出状态和通过/失败/跳过证据。
- R3：追踪真实失败的工作流根因，区分当前本地、历史远端、环境限制和未验证能力。
- R4：按问题映射适用 harness 与强模型规划/审查、低成本模型执行边界。
- R5：给出有优先级的改造项、文件范围、依赖顺序与必须通过的检查。
- R6：审查 AGENTS.md、CLAUDE.md、五套工具规则及用户安装说明的冲突和缺失。
- R7：创建父子任务；批准后的经验按适用工具回写项目说明、skill 库或团队知识库。

## Authority

用户已明确授权本轮审查、测试、只读远端取证及 Trellis 规划材料写入。本轮所有父子任务保持 planning，不运行 task.py start，不修改产品代码、正式说明、全局配置或共享记忆，不提交或推送。README.md、README_CN.md 为进入任务前已有改动，保留原状。后续实施以用户对最终计划的明确批准为前提。

## Acceptance Criteria

用户已确认保留“仅限学术、禁止商业使用”的许可方向；后续仅统一冲突声明，不自行增加法律条款。具体文件范围、六个子任务和依赖顺序见 design.md 与 implement.md。

- [ ] AC1（R1/R6）：结构与规则审查有当前文件锚点；每套 harness 区分项目入口、skill 发现、委派、权限和上下文机制。
- [ ] AC2（R2/R3）：测试台账包含真实失败及最小复现；远端 run 与本地 SHA 的证据边界清楚，不把历史成功视为当前门禁。
- [ ] AC3（R4）：每个改造问题/子任务均映射适用 harness 及其证据状态；高风险判断由强模型负责；适合低成本执行的任务有输入、文件边界、升级条件和复核门禁，不将 harness 品牌当作模型价格。
- [ ] AC4（R5/R7）：父子任务均有具体需求、设计、执行步骤及非示例上下文清单，文件范围与验证命令可执行。
- [ ] AC5（R6/R7）：计划明确批准后回写位置和适用工具；五工具真实启动/加载/委派没有证据时明确 UNVERIFIED。
- [ ] AC6（R5/R7）：本轮只有任务规划材料新增，已有 README 改动不变，计划经独立强模型审查后交用户批准。

## Non-goals

本轮不进行全面重构、依赖升级、全局工具安装、付费模型试跑、生产部署或知识库写入；不把动态模型推荐硬编码为永久能力声明。
