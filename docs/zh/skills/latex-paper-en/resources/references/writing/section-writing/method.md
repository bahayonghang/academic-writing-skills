# 方法部分写作

## 目标

方法部分应当可复现且有充分理由。读者无需反推作者意图，即可追踪每个模块为何存在、输入
如何变为输出，以及该输出如何进入下一模块。

## 写作前表格

起草前，先整理每个模块：

| 模块 | 输入 -> 输出 | 为何需要 | 为何有效 | 后续证据 |
| --- | --- | --- | --- | --- |
| ... | ... | ... | ... | 表格/消融/分析 |

如果某个模块没有动机或后续证据，在写正文前标记该缺口。

随后整理每条相邻边：

| 上游模块 | 上游输出 | 连接类型 | 中间变换 | 下游用途 |
| --- | --- | --- | --- | --- |
| A | `z_A` | 串行数据 | 对齐/投影 | B 的直接输入 |
| B | 候选集合 | 校准/选择 | 阈值与预算筛选 | C 的监督信号 |

当每对相邻模块都有一行，且输出、中间变换和下游用途均已填写时，此表格才算完成。

## 章节结构

1. **总体介绍**：任务与数据契约、共同输入、模块分工、执行顺序、训练/推理差异、最终输出和
   流程图引用。
2. **模块小节**：每个技术模块或独立设计单元使用一个小节。
3. **实现细节**：超参数、归一化、训练设置、工程选择、更新/冻结状态、停止条件和回退路径。

当总体介绍中的数据流与图、公式和伪代码一致时，总体介绍才算完成。

## 模块三要素

每个方法小节应当覆盖：

1. **动机**：哪个挑战或失效模式要求引入此模块。
2. **设计**：具体的表征、网络、数据结构、算法或前向过程。
3. **技术优势**：为何此设计比备选方案更适合当前问题，最好关联到可测量行为。

同时补全局部契约：写明输入、关键变换、输出语义和下游使用者。一个角色可以用一句或一段
表达，无需套用固定报幕句式。

## 模块间接口契约

对每对相邻模块，写明上游输出、连接变换和下游用途。

| 连接类型 | 判据 | 正文必须说明的内容 |
| --- | --- | --- |
| 串行数据 | A 的输出直接成为 B 的输入 | 名称、形状、语义和投影变换 |
| 并行表征 | A 与 B 共享输入并分别构建表征 | 融合位置和融合规则 |
| 监督/目标 | A 为 B 产生标签、区间、权重、损失或约束 | 信号进入 B 目标函数的位置 |
| 校准/选择 | A 产生候选，B 决定准入或排序 | 准入规则；候选不等于最终样本 |
| 反馈/控制 | 下游评价更新上游对象 | 反馈量、更新对象和停止条件 |
| 剩余约束 | A 解决一个限制，但暴露另一个限制 | 需要 B 处理的未解决约束 |

**M-NONDIRECT。** 两个模块没有直接数据依赖时，应当排除最可能的误读：

> B 不以 A 的预测结果为条件。二者共享相同的输入语义，并通过 C 构建的监督关系相连。

只有读者能够确定生产者、变换和使用者时，该接口才完整。

## 公式论证完整性

每个关键公式应当形成 `purpose -> equation -> symbol gloss -> output semantics -> downstream use`。
公式前写明所需计算和输入对象；公式后定义新符号，说明公式产生的对象，并指出下游使用者。

符号一致性与公式论证完整性是两项不同检查。符号一致性检查名称或含义是否冲突；公式论证
完整性检查目的、符号释义、输出或下游连接是否缺失，即使符号内部一致也要检查。公式顺序
应当遵循计算顺序；如果推导顺序不同，应当明确说明理由。

## 标题使用

行内小标题可以导航独立技术单元，但不能替代因果关系和接口关系。连续使用
`\paragraph{Fusion.} This module is used to ...` 一类结构时，如果正文只复述职责，就会形成
报幕式脚手架。

问题不在标题本身。具有真实输入/输出契约的方法小节是合法的，以证据为先的实验结果引导标题与
[`style-guide.md`](../style-guide.md#related-work) 中的 Related Work 分组模式同样合法。分别审阅每个模块的首段和末段；
只读这些段落仍能看出当前约束、模块输出和下一步用途时，方法链才清晰。

## 证据分级

先确定主张类型，再选择主张强度。[`claim-evidence-contract.md`](../../evidence/claim-evidence-contract.md)
给出证据强度上限；[`over-claim-guard.md`](../../evidence/over-claim-guard.md) 给出该上限内的措辞。

| 主张类型 | 最低可见依据 | 方法部分中的强度上限 |
| --- | --- | --- |
| 定义事实 | 直接定义该事实的公式或算法 | `supported`，且仅限定义范围 |
| 机制级作用 | 结构、复杂度或逻辑推导 | `supported`；不能写成经验性能结论 |
| 经验性能 | 指标与适用设置；更广结论还需比较产物 | 局部为 `observed`；只有匹配证据才能达到 `supported/strong` |
| 因果归因 | 可区分的消融、干预或证明 | 仅在对应设计范围内达到 `strong`；否则不作因果主张 |

「improves」「enhances」「effectively solves」等词不能产生证据。如果只看得到设计依据，
应当说明此设计用于什么，或它在定义上保证什么。

## 写作顺序

1. 锁定公式、符号、引用、数值、数据划分和已报告结果。当每项受保护事实都有明确来源位置时，
   此步骤完成。
2. 绘制模块图，填写输入、变换、输出、训练/冻结状态和回退路径。当每个核心模块的适用字段
   均已填写时，此步骤完成。
3. 填写相邻边表。当图中的每条边都有连接类型和下游用途时，此步骤完成。
4. 先改写总体介绍和模块间过渡，再处理模块内部句子，最后调整标题。当正文与模块图表达相同
   的边顺序时，此步骤完成。
5. 逐个检查关键公式的目的、符号释义、输出语义和下游用途。当没有缺失角色时，此步骤完成。
6. 将每项收益主张映射到上述证据分级。当所有措辞均未超过可见依据时，此步骤完成。
7. 只读每个模块的首段和末段。当这些段落仍能还原完整方法链时，此步骤完成。

## 硬性边界

- 不得编造公式、超参数、算法步骤、复杂度主张、证据或实现细节。
- 细节缺失时，写出面向审稿人的 TODO，不得自行补全。
- 除非任务明确要求编辑源码，否则原样保留数学内容、宏、label、citation、数值和图引用。

## 诊断

仅对方法范围运行候选检查：

```bash
uv run python -B scripts/analyze_logic.py main.tex --section methods
```

将 `M-HEADING`、`M-SEQWORD` 和 `M-EQUATION` 视为需要 LLM 复核的 `[Script]` 候选。
改写模块过渡前，填写脚本输出的 `M-EDGETABLE`。
